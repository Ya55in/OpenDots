# Original Word templates and document previews

When a user refers to an existing order, proposal or branded document, Dots can find the original `.docx` in their own file library or in verified migrated archives. Archive lookups use bounded random access to SQLite chunks; they do not unpack the whole archive or write archive paths to disk.

The agent workflow is `find_word_templates` → `inspect_word_template` → `edit_word_template` → `review_document`. Text edits address an XML part, paragraph number and exact unique old text. Runs retain their formatting; unchanged package parts retain their original bytes. Header/footer text and table cells are supported. This is a text-editing workflow; adding rows, changing drawings and rewriting fields or tracked changes is not yet supported. Prefer unsigned drafts and never treat an old signature as authorization to sign a new document.

The downloadable PDF is rendered from the edited DOCX with LibreOffice. Poppler creates page images. The chat and file library offer authenticated Preview buttons, navigation and review observations. The dedicated inexpensive vision route reviews actual page images in batches. With routing enabled, `ROUTER_V2_REVIEW_MODEL` selects it; legacy `DOCUMENT_REVIEW_MODEL` only applies without the router. Reviews share the initiating turn’s dollar and call budgets. A review applies to the SHA-256 digest of the file, checks every page, and is only saved after every batch succeeds. Visual review does not verify business facts or guarantee perfection. Agents must read observations and revise reported problems.

Runtime packages are installed by `railpack.json` and the app Docker image: LibreOffice Writer, Poppler, fontconfig, Carlito, Caladea, Liberation, DejaVu and Noto fonts. DOCX retains original font declarations; PDF font substitutions are reported explicitly. For exact proprietary font fidelity, install the appropriately licensed original fonts in the server image. Do not silently promise pixel-identical Microsoft Word rendering.

Limits: DOCX/PDF 25 MB, expanded Word package 80 MB/2,000 entries, two concurrent render jobs, 60 seconds per native command, 30 pages/20 MB of previews per document, 50,000 entries per migrated archive. Macros, external resources other than HTTP(S) hyperlinks, DDE fields, embedded objects and digitally signed packages are rejected. Rendering uses private temporary directories, isolated LibreOffice profiles, disabled macros and link updates, restricted child-process environment, and no shell-interpolated document values. Temporary files are removed after success or failure.

Files save to the Dot's connected Google Drive folder, or local Space storage. If PDF rendering fails, the edited DOCX remains downloadable and the tool reports the failure. Failed visual review never becomes a successful review badge. Original files are never overwritten.

## Original presentation designs

`find_presentation_templates` searches the Dot's PPTX files and verified migrated archives, including skill assets. `inspect_presentation_template` reads original slide objects, shape IDs, paragraph text, dimensions, fonts and pictures. Its `visualSlides` option asks the configured vision model to inspect selected source designs. For VYANIS hospitality work, search the original Limoune workshop; the skill's premium-design reference is the general visual direction.

`create_presentation_from_template` accepts the complete ordered slide plan. Source slides can be selected, reordered and duplicated, with exact edits to individual text paragraphs. Masters, layouts, imagery, theme, geometry and unaffected object formatting remain original. Source notes, comments, old document properties and excluded slides are removed, and unreachable resources are pruned. No old client facts or pricing become approved facts for a new project. Text embedded in artwork cannot be edited, and internal slide links must be removed before changing slide order. This is a template adaptation workflow, not unrestricted illustration generation or chart/workbook editing.

The PPTX is rendered by LibreOffice Impress into its matching PDF and authenticated slide previews. `review_presentation` compares every output slide with its mapped source slide using the actual rendered images. The saved review includes the reference digest and is also applied to the matching PDF preview. Completion means all slides were inspected; the agent must read findings, fix problems and review again. Neither commercial facts nor pixel-identical Microsoft PowerPoint rendering are guaranteed. Original font declarations are retained; missing PDF fonts are reported.

The generic Markdown slide tool is deliberately gated behind `plainSlides=true`, reserved for a user-requested plain text draft. It must not silently substitute for a branded presentation. PPTX preview is available in both generated file cards and the file library. LibreOffice Impress is installed in Railpack and Docker runtime images. The existing 25 MB file and 30-page review limits apply.

Agent turns have a ten-minute wall-clock deadline so multi-step template discovery, rendering and visual review can complete. Stop, pause and access revocation still cancel running work; per-command and review-request deadlines remain shorter. The agent loop and provider output limits remain bounded.

Presentation/document tasks allow up to 20,000 output tokens for complete slide edit plans. Ordinary responses use 2,000/4,000/8,000-token ceilings by task tier. Per-call cost reservations can block an expensive plan before it is sent. These are ceilings, not requested response lengths.
